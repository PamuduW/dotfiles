## dotfiles

### Defects

**D1. Failed font rollback deletes the recovery copy**

**Severity: medium.** `scripts/lib/installers/fonts.sh:30` registers a RETURN trap that deletes `backup_dir`. After moving the existing installation there, activation failure attempts restoration with `mv … || true` at line 72. If restoration also fails, returning runs the trap and deletes the remaining old installation. This is a static finding; no installation or failure injection was performed.

Smallest fix: retain and report `backup_dir` when restoration fails.

**D2. Cursor’s preview and updater recognise different executable names**

**Severity: medium.** `scripts/lib/updates/integrations.sh:11` and line 23 resolve `agent cursor`; the updater at line 47 resolves `agent cursor-agent`. The installer also recognises `cursor-agent`. A supported installation exposing only `cursor-agent` therefore appears absent in the preview but can be updated during apply. Conversely, a Linux editor launcher named `cursor` can be mistaken for the CLI during preview.

Smallest fix: use `agent cursor-agent` consistently in the version reader, presence check and updater.

### Security

**D3. Monaspace is installed without integrity verification**

**Severity: high.** `scripts/lib/installers/fonts.sh:31` downloads the release ZIP and line 36 extracts it without checking a published digest or checksum. The path check at lines 41–47 runs **after** extraction. Unlike the moving vendor-shell channels documented in `docs/security.md`, this release-archive exception is not recorded.

HTTPS protects transport, but there is no artifact verification boundary before the downloaded fonts replace the installation.

Smallest fix: verify the selected release asset’s published SHA-256 digest before extraction, and inspect archive members before unpacking.

## agentbot

### Defects

**A1. Reconciliation removes customised skills without checking their receipts**

**Severity: high.** `src/skill_reconcile.py:137–153` selects removals from source ownership alone. It does not compare current content with `skillFolderHash`. Lines 387–398 then delete the directory and owned links; line 442 deletes the successful transaction’s backup.

This bypasses the protection documented in `docs/skills.md:74–81`: changed skills belong to the user. An upstream deletion of an explicitly selected skill, or a wildcard removal, can therefore remove local customisations.

A read-only, in-memory probe confirmed that `_approved_lock_mutations()` selects a receipt-bearing skill for removal without receiving or checking its current content.

Smallest fix: apply the same modified-skill receipt check used by pruning before scheduling any reconciliation removal.

**A2. Skills-only updates do not snapshot ordinary updates for rollback**

**Severity: high.** `src/skills_installer.py:882–889` calls `apply_reconcile_plan()` with the installer as its validation callback but no `extra_affected` paths. `src/skill_reconcile.py:360–370` snapshots only added/removed names and associated metadata.

When source revisions change without changing skill names, the snapshot is empty. If installation updates earlier sources and a later source fails, rollback cannot restore those earlier skills or their newly written lock entries. This contradicts the transaction promise in `docs/skills.md:15–21`.

An in-memory probe intercepted `_snapshot()` and observed an empty path list for this case. The full lifecycle update supplies broader paths at `src/lifecycle.py:527`; the skills-only path does not.

Smallest fix: snapshot the lock, skill store and managed skill bridges before the skills-only installer runs.

**A3. Selected skills reference support files that selective installation omits**

**Severity: medium.** The prepared source copies contain these references, but read-only existence checks confirmed that their installed targets are absent:

### Security

**A4. GitLab token verification forwards its credential across redirects**

**Severity: high.** `src/gitlab_token.py:252–257` adds `PRIVATE-TOKEN` to a request and calls default `urllib.request.urlopen()`. Default redirect handling retains that custom header when constructing a request to another origin.

A synthetic, network-free check against the installed Python redirect handler confirmed that a cross-origin redirect retained `PRIVATE-TOKEN`. No real credential or HTTP request was used. Exploitation requires a redirect from the configured verification endpoint; no such redirect was observed.

The GitLab MCP client already handles this boundary explicitly: `src/gitlab_read_client.py:86` disables automatic redirects and line 431 rejects cross-origin redirects.

Smallest fix: disable redirects during token verification, or validate each redirect’s HTTPS origin before resending credentials.

**A5. GitLab tokens survive both memory scanning and review-report masking**

**Severity: high.** `src/memory.py:802–846` recognises GitHub, OpenAI, AWS and private-key patterns, but no GitLab token prefix. `src/setup_review.py:820` reuses that rule set. Its additional setting-name filter does not catch a token embedded in ordinary prose.

A synthetic GitLab-shaped value produced **zero scanner findings** and survived `redact_report()` unchanged. No real credential was read. `write_report()` uses that masker at line 993, and setup review can subsequently publish the cleaned report.

Smallest fix: add a GitLab-token blocking/redaction rule and regression cases covering prose, diagnostics and report output.
